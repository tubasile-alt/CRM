## 2. Ambiente de deploy — Autoscale

`.replit` → `deploymentTarget = "autoscale"`,
run `gunicorn --config gunicorn.conf.py app:app`.
`gunicorn.conf.py` → `workers=2, threads=2, timeout=120, preload_app=True`.

### 2.1 O que o Autoscale NÃO quebra

**A geração de dispatch está segura.** Ela é event listener SQLAlchemy
(`followup_service.py:139,147`), executado dentro do request que marca a
execução como `realizada`. Não depende de scheduler nem de instância acordada.

Isso invalida a ideia original de um job APScheduler às 06:00 — no Autoscale
seria não-confiável. A implementação atual é melhor.

### 2.2 O que o Autoscale quebra

**a) Scheduler interno não-confiável.** `app.py:4108-4139` pendura dois jobs:
`mark_no_shows_grace_minutes(30)` a cada 5 min e `run_botox_sheet_sync()` a
cada 6 h. Com zero instâncias, nenhum roda. Problema anterior à Fase 4.

*Inferência não verificada:* com `preload_app=True`, o `app.py` é importado no
processo master antes do fork. A thread do APScheduler nasce no master e não é
herdada pelos workers. O provável é que os jobs rodem só no master — funciona,
mas some quando a instância dorme.

Teste para confirmar: conte quantas vezes `[AUTO-FALTOU] Scheduler iniciado`
aparece no log de deploy (1 = só master; 3 = master + 2 workers) e verifique se
houve algum `[BOTOX-SHEET]` nas últimas 24 h. Nenhum = job morto.

**b) Cold start vs. chamada do n8n.** Às 13h e 19h30 a instância estará
dormindo. A primeira request paga boot + import do `app.py` (4.261 linhas) +
preload. E `/due` faz a query mais pesada da rota justamente nessa request.

Resolve-se **no n8n, sem tocar no CRM**: GET de aquecimento numa rota leve ~60 s
antes, timeout de 90 s na chamada real, 2 retries com backoff.

**c) Cap diário não é atômico entre instâncias.** Tratado no PR2.

### 2.3 Risco no post-merge

`.replit` → `[postMerge] path = "scripts/post-merge.sh"`, `timeoutMs = 120000`
→ `python migrate_db.py`.

`migrate_db.py` roda `backup_database()` antes de tudo. Conforme o banco cresce,
isso vai estourar os 120 s e o post-merge morre no meio da migração. Monitorar.

## 4. PR2 — Reserva atômica no `/due`

Branch sugerida: `feat/dispatch-reserva-atomica`.

### 4.1 Problema

`routes/integrations.py:143` faz `_pending_query().all()`, corta em memória e
devolve — sem marcar nada. Duas chamadas concorrentes recebem a mesma lista.
Com Autoscale (N instâncias) + gunicorn (4 handlers por instância) + retry do
n8n após cold start, isso vira disparo duplicado para o mesmo paciente.

### 4.2 Janela segura — a correção de fuso entra AQUI, não no PR3

`sent_at` está **NULL em todas as linhas**: nunca houve PATCH bem-sucedido,
porque a API key nunca foi configurada e as rotas retornam 503.

Por quê isso importa: `get_brazil_time()` (`services/clinic_time.py:21`)
devolve datetime **aware** em São Paulo, mas as colunas são `db.DateTime` sem
`timezone=True` — o Postgres guarda o wall clock local. Já `sent_at` grava
`datetime.utcnow()` (`integrations.py:216`), naive em UTC. A coluna acabaria
com dois fusos misturados.

Como ainda não há nenhum `sent_at` gravado, a correção é trivial agora e vira
migração de dados depois do go-live.

| Linha | Hoje | Vira |
|---|---|---|
| `integrations.py:75` | `date.today()` | `clinic_today()` |
| `integrations.py:91` | `date.today()` | `clinic_today()` |
| `integrations.py:216` | `datetime.utcnow()` | `get_brazil_time()` |

Impacto prático hoje é baixo (13h e 19h30 BRT caem no mesmo dia UTC), mas
qualquer batch que escorregue depois das 21h BRT reseta o cap um dia antes.

### 4.5 Recuperação de reservas órfãs — inline, sem scheduler

Decisão deliberada: roda no começo do próprio `/due`, não num job, porque no
Autoscale scheduler não é garantia.

```python
def _reclaim_stale_reservations():
    from models import MessageDispatch, db

    limite = get_brazil_time() - timedelta(minutes=_reservation_ttl())
    devolvidas = db.session.query(MessageDispatch).filter(
        MessageDispatch.status == 'reservada',
        MessageDispatch.reserved_at < limite,
    ).update(
        {'status': 'pendente', 'reserved_at': None},
        synchronize_session=False,
    )
    if devolvidas:
        db.session.commit()
    return devolvidas
```

Coberto pelo índice `ix_dispatch_reservada`. Custo desprezível.

### 4.6 Seleção com trava

```python
def _lock_pending(limit):
    """SELECT ... FOR UPDATE SKIP LOCKED dos vencidos elegíveis."""
    from models import MessageDispatch, Patient, db

    query = (
        db.session.query(MessageDispatch, Patient)
        .join(Patient, Patient.id == MessageDispatch.patient_id)
        .filter(
            MessageDispatch.status == 'pendente',
            MessageDispatch.due_at <= clinic_today(),
            Patient.phone.isnot(None),
            Patient.phone != '',
            Patient.accepts_marketing.is_(True),
        )
        .order_by(MessageDispatch.due_at.asc(), MessageDispatch.id.asc())
        .limit(limit)
    )

    if db.session.get_bind().dialect.name == 'postgresql':
        query = query.with_for_update(of=MessageDispatch, skip_locked=True)

    return query.all()


def _reserve(dispatches):
    from models import db

    agora = get_brazil_time()
    for dispatch in dispatches:
        dispatch.status = 'reservada'
        dispatch.reserved_at = agora
    db.session.commit()   # o commit solta a trava das não-selecionadas
```

**Três detalhes que não são opcionais:**

1. **`of=MessageDispatch`.** Sem isso o `FOR UPDATE` trava também as linhas de
   `patient` — e o CRM inteiro trava para editar aqueles pacientes enquanto o
   n8n roda. É o erro mais caro possível neste PR.
2. **Guarda de dialeto.** `skip_locked` é Postgres. Produção é `postgresql-16`,
   mas se algum teste ou script rodar SQLite, sem a guarda quebra.
3. **Over-fetch.** `LIMIT n FOR UPDATE SKIP LOCKED` no Postgres pode devolver
   menos que `n` (o LIMIT é aplicado antes do skip). Chame com `limit * 3` e
   corte depois.

### 4.7 Cap diário passa a contar reservadas

Senão o cap é contornável: o n8n chama duas vezes antes de confirmar qualquer
envio e reserva 40 com cap de 20.

```python
def _consumed_today():
    from models import MessageDispatch, db

    hoje = clinic_today()
    return db.session.query(db.func.count(MessageDispatch.id)).filter(
        db.or_(
            db.and_(
                MessageDispatch.status == 'enviada',
                db.func.date(MessageDispatch.sent_at) == hoje,
            ),
            db.and_(
                MessageDispatch.status == 'reservada',
                db.func.date(MessageDispatch.reserved_at) == hoje,
            ),
        )
    ).scalar() or 0
```

Substitui `_sent_today()` no cálculo do `remaining`. Mantenha `_sent_today()`
vivo para o campo `sent_today` da resposta — é o número que interessa no
relatório.

### 4.8 Nova ordem em `messages_due`

```
1. mode == 'off'            → retorna, sem tocar no banco   (preserva o teste atual)
2. _reclaim_stale_reservations()
3. remaining = cap - _consumed_today()
4. remaining == 0           → retorna
5. rows = _lock_pending(min(limit, remaining) * 3)
6. filtro de whitelist (modo test) — em Python, dentro da transação
7. selecionadas = rows[:min(limit, remaining)]
8. _reserve(selecionadas)   → commit
9. serializa
```

O filtro de whitelist **precisa** ficar entre 5 e 8. Se reservar antes de
filtrar, os números fora da whitelist ficam presos em `reservada` por 30 min a
cada chamada.

### 4.9 O detalhe que trava a fila inteira se for esquecido

`routes/integrations.py:213` tem hoje:

```python
if dispatch.status != 'pendente':
    return jsonify({... 'note': 'já processado, sem alteração'})
```

Com reserva, **todo dispatch chega no PATCH em `reservada`**. Se esse guard não
mudar, cada confirmação do n8n é ignorada, nada vira `enviada`, e em 30 min tudo
volta para a fila — loop silencioso de reenvio, sem erro em lugar nenhum.

```python

    return jsonify({...})

dispatch.status = new_status
dispatch.reserved_at = None          # libera em qualquer desfecho
dispatch.sent_at = get_brazil_time() if new_status == 'enviada' else None
```

Aceitar `pendente` também mantém compatibilidade com um PATCH que chegue fora do
fluxo de reserva.

### 4.13 Contrato com o n8n — o que muda do lado de lá

Nada obrigatório, mas dois comportamentos novos:

- **Retry depois de timeout não duplica.** Se o n8n receber o lote e estourar
  antes de confirmar, aquelas mensagens ficam travadas por até 30 min e o retry
  pega um lote diferente. Efeito: atraso, nunca duplicata.
- **Confirmar passa a ser obrigatório.** Antes, não mandar o PATCH só deixava a
  linha pendente. Agora, não confirmar consome cap até o reclaim. Se o n8n não
  confirmar, a fila anda devagar em vez de travar — mas anda devagar.

## 7. Sequência de ativação

Uma trava por vez, nessa ordem:

1. **`INTEGRATIONS_API_KEY`** → rotas saem do 503. Gerar com
   `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
   Não repetir o valor em chat nem em log.
2. **`MESSAGE_DISPATCH_ENABLED=1`** → passa a gerar dispatch de aplicações
   novas. Nada é enviado (`SEND_MODE=off`).
3. **`python scripts/backfill_botox_dispatches.py --dry-run`** → conferir os
   números. Depois `--commit`.
4. **`DISPATCH_SEND_MODE=test`** + `DISPATCH_TEST_PHONES` só com o seu número.
5. **`DISPATCH_SEND_MODE=live`**, com `DISPATCH_DAILY_CAP=20`.

O passo 2 vem antes do 3 de propósito: se ficar off, toda aplicação registrada
nesse intervalo não gera dispatch, e o listener **não é retroativo** — só o
backfill recupera.

## 8. Regras de trabalho

1. **Nada de envio.** O CRM não manda mensagem. Ele monta e registra a fila.
